# cdp_capture 核心原理说明

## 1. 这个工具是做什么的

`cdp_capture.py` 用来从一个已经打开的 Chromium 页面里抓取网络数据。

它支持两类数据：

- WebSocket 消息
- HTTP 请求/响应

它不是浏览器自动化工具，不负责打开浏览器、创建页面或操作页面。它只做一件事：连接到一个已经存在的页面，然后监听这个页面后续产生的网络事件。

## 2. 核心思路

它的工作方式可以概括成 4 步：

1. 连接浏览器的 CDP 调试地址
2. 选中一个目标页面
3. 监听这个页面的 `Network` 事件
4. 把抓到的数据按 JSONL 写到文件里

所以它本质上是一个“基于 CDP 的页面网络监听器”。

## 3. 为什么能抓到这些数据

因为 Chromium 提供了 Chrome DevTools Protocol（CDP）。

只要浏览器开启了远程调试端口，脚本就可以：

- 先通过 HTTP 接口拿到当前有哪些页面
- 再连接到某个页面对应的 CDP WebSocket
- 打开 `Network` 域监听
- 持续接收这个页面的网络事件

这些事件里已经包含了 WebSocket 建连、收发帧、HTTP 请求开始、响应到达、请求完成等信息。脚本做的事情，就是把这些事件整理成更容易使用的结构化记录。

## 4. WebSocket 是怎么抓的

WebSocket 的逻辑很直接：

- 页面建立 WebSocket 连接时，记录连接的 `requestId` 和 URL
- 页面收发 WebSocket 帧时，取出方向、内容、opcode
- 把这些信息写成一条 JSON 记录

可以理解成：

- `webSocketCreated` 负责记住“这是哪条连接”
- `webSocketFrameSent` / `webSocketFrameReceived` 负责记住“这条连接发了什么、收了什么”

这样最终就能得到一份按时间追加的 WebSocket 消息日志。

## 5. HTTP 是怎么抓的

HTTP 比 WebSocket 多一步“拼装”。

因为一次 HTTP 请求的信息不是在一个事件里同时给出的，而是分散在几个阶段：

- 请求发出时，拿到请求方法、URL、请求头、请求体
- 响应到达时，拿到状态码、响应头、MIME 类型等
- 请求结束时，再去拉取响应体

所以代码里会先按 `requestId` 暂存请求信息，等请求完成后再拼成一条完整记录输出。

可以把它理解成：

- 前两个事件先收集材料
- 最后一个事件再组装成成品

## 6. 为什么要分 raw 和 match

输出文件分成两类：

- `raw`：尽量保留原始抓取结果
- `matches`：只保留命中过滤条件的结果

这样设计的原因很简单：

- 想完整排查时，可以看 raw
- 只关心某些关键字时，可以直接看 matches

也就是说，这个工具同时支持“全量留存”和“按条件筛选”两种使用方式。

## 7. 过滤规则的原理

过滤规则分两层：

- 先按 URL 过滤
- 再按消息体或响应体过滤

匹配方式支持两种：

- 普通字符串子串匹配
- `re:` 开头的正则匹配

所以它不是复杂查询系统，而是一个轻量、够用的文本过滤器。

## 8. 为什么有 `--reload`

因为脚本只能看到“它连上之后”发生的事件。

如果某个 WebSocket 连接早就建好了，或者某些 HTTP 请求早就完成了，那么脚本后连上去是看不到之前那部分过程的。

`--reload` 的作用就是在附着成功后主动刷新一次页面，让页面重新发起初始化阶段的网络请求，这样更容易抓到完整数据。

## 9. 输出为什么用 JSONL

因为 JSONL 很适合这种持续追加的流式日志场景：

- 一行一条记录
- 便于实时写入
- 便于后续用脚本处理
- 出问题时也容易人工查看

这个格式比一次性写一个大 JSON 更适合长时间监听。

## 10. 当前设计边界

这个工具的边界也很明确：

- 一次只盯一个页面
- 只抓附着后的事件
- 不负责浏览器启动和页面操作
- 主要目标是“简单可靠地抓数据”，不是做复杂自动化框架

所以它的定位一直是“小而直接”的调试工具，而不是通用浏览器采集平台。

## 11. 一句话总结

`cdp_capture.py` 的核心原理就是：

通过 CDP 连接到一个已经打开的浏览器页面，监听它后续产生的 WebSocket 和 HTTP 网络事件，再把这些事件整理后持续写入 JSONL 文件。
